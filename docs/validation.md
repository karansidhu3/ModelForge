# Validation Philosophy

## Starting assumption

Every implementation is assumed incorrect until it's been checked against
something external to itself — a known answer, a hand computation, a published
worked example. "It runs without crashing" and "it produces numbers that look
plausible" are both explicitly insufficient. Validation exists to catch the
failure mode where a formula is subtly wrong (an off-by-one in a rolling
window, a variance computed with the wrong denominator, a lookahead bug) but
still produces output that looks fine at a glance.

## What every model must provide

- **Known inputs and known outputs.** At least one test case where the
  expected output is taken from the source material, a textbook worked
  example, or an independently hand-computed result — not generated by
  running the implementation itself and asserting it matches.
- **Edge cases, explicitly.** Empty input. Input shorter than the required
  window. NaNs in the input series. A constant series (zero variance). These
  are test cases, not comments saying they should probably be handled.
- **Documented assumptions.** What the model assumes about its input (evenly
  spaced observations, no missing trading days, a particular convention for
  returns vs. log-returns) is written down in `research/<model>/README.md`,
  not left implicit in the code.
- **Inspectable intermediate calculations**, where a calculation has
  meaningful intermediate steps. A z-score, for example, should make its
  rolling mean and rolling standard deviation inspectable, not just the final
  score — so a researcher can see *where* a surprising result came from.

## The validation framework vs. unit tests

These are complementary, not redundant:

- **Unit tests** run at development time and CI time. They check that the
  implementation matches known answers and handles edge cases. They are
  written once per model and don't run as part of a production pipeline
  execution.
- **The validation framework** (`core/validation.py`) runs as part of every
  pipeline execution, at runtime, against whatever data was actually loaded
  for that run. It performs baseline structural checks (correct output
  shape, no unexpected NaNs propagating past where they should have been
  handled, output aligned to the input index) and, where a model's config
  specifies known-answer fixtures, a numerical spot check against them.

In short: unit tests validate the *code*. The validation framework validates
each *run*.

## Why this is a separate layer instead of assertions inside each model

Putting validation logic inside every model's implementation means its rigor
depends on what that model's author remembered to check. A shared validation
layer in `core/` guarantees every model — including ones that don't exist yet —
gets the same baseline scrutiny. See `DESIGN_DECISIONS.md`, DD-006.

## What validation does not do

It does not judge whether a result is a *good* result in a financial sense —
that's explicitly out of scope for this project (see the non-goals in
`CLAUDE.md`). It judges whether a result is a *correct* computation of what the
model claims to compute.
