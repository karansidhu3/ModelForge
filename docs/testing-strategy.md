# Testing Strategy

## What testing is for, here

Not coverage percentage. Not "the function ran without raising." Testing
exists to demonstrate — to a reader who didn't write the code — that a model's
implementation matches its mathematical definition, and that it fails
predictably (rather than silently) on inputs it can't handle correctly.

## Tooling

`pytest`, exclusively. No other test runner. Tests live under `tests/`,
mirroring the structure of `src/modelforge/` so any module's tests are easy to
locate.

## What every model's test suite must include

1. **Known-answer tests.** At least one test where the expected output comes
   from the source research, a textbook worked example, or an independent
   hand computation — never generated by running the implementation and
   asserting the output equals itself.
2. **Edge cases, as explicit test functions:**
   - Empty input series.
   - Input shorter than `required_history`.
   - NaNs present in the input.
   - A constant series, where relevant (e.g. zero variance for
     volatility/z-score models).
3. **No-lookahead tests.** Where feasible, a test that perturbs data *after*
   a given index and asserts the factor's output *at* that index is
   unchanged — a direct check against the no-lookahead guarantee in
   `docs/factor-interface.md`.
4. **Determinism.** Running a model twice against the same input and config
   produces bit-identical output. If a model ever needs randomness, this
   becomes "produces identical output given the same seed" instead — and the
   seed is part of its config.

## What tests must not do

- Depend on live network calls. `data/` loaders are tested against local
  fixture files or mocked responses, never by actually hitting Yahoo Finance
  or FRED in CI.
- Depend on wall-clock time or system timezone.
- Depend on execution order between test functions.
- Assert against the implementation's own output as the "expected" value —
  that tests that the code didn't change, not that it's correct.

## Fixtures

Shared, deterministic fixture datasets (small synthetic CSVs with known
properties) live under `tests/fixtures/` once Phase 2 begins, so multiple
models' tests can reuse the same known series rather than each inventing its
own.

## Coverage as a signal, not a target

Coverage tooling (`pytest-cov`) is used to catch obviously untested branches,
not chased as a number. A model with 100% line coverage and no known-answer
test has not been validated in any sense this project cares about; a model
with a solid known-answer test and thorough edge-case coverage, even at lower
line coverage, has.

## Relationship to the validation framework

Unit tests and the runtime validation framework (`docs/validation.md`) are
deliberately separate. Tests validate the code once, at development time.
The validation framework validates every actual run, at execution time,
against whatever data was really loaded. Neither substitutes for the other.
